# 缓存设计

## 缓存解决什么问题

生成配置和预览都会读取远程资源。同一个 URL 在短时间内通常无需重复下载，`CachedFetcher` 因此将成功响应保留一段时间。这个保留时间称为 TTL，由 `-cache-ttl` 设置，默认 5 分钟。

缓存只存在于当前进程内，重启后清空。启动入口创建一个 `CachedFetcher`，供配置读取、生成和预览共用。实现见 [cache.go](../../internal/fetch/cache.go)，装配见 [main.go](../../cmd/subconverter/main.go)。

## 哪些内容会缓存

| 资源 | 读取方式 | 缓存行为 |
|------|----------|----------|
| 订阅、Snell、VLESS 来源 | HTTP(S) | 按完整 URL 缓存响应体 |
| 远程底版模板 | HTTP(S) | 使用同一缓存和 TTL |
| 远程主配置 | HTTP(S) | 使用同一缓存；热重载时单独清除该 URL |
| 本地主配置或底版模板 | `os.ReadFile` | 每次直接读文件 |
| 远程规则集正文 | 由 Clash / Surge 客户端拉取 | 服务端只输出 URL，不读取正文 |

缓存键是完整 URL，包括查询参数。更换 URL 会使用不同的缓存项；相同 URL 即使被用于不同资源，也会共用一项。

## 一次读取怎样完成

调用 `Fetch(ctx, rawURL)` 时：

1. 短暂加锁，查找该 URL。缓存项存在且距离上次成功拉取未满 TTL 时，返回响应体副本。
2. 未命中或已过期时，释放锁，再通过内部 `Fetcher` 拉取资源。
3. 拉取成功后，把响应体副本和完成时间写入缓存，再向调用方返回副本。
4. 拉取失败时直接返回错误。错误不写入缓存，也不退回到已经过期的旧响应。

复制响应体是为了让调用方可以处理自己的字节切片，而不会改坏其他请求将读到的缓存内容。网络请求在锁外执行，所以一个慢来源不会占着缓存锁。

当前缓存没有合并同一 URL 的并发下载：两个请求同时发现缓存未命中时，都可能访问上游。过期条目也没有后台清理；再次读取同一 URL 时才会判断过期并在成功拉取后覆盖。当前单用户设计保留这些边界。

TTL 既影响请求次数，也决定普通读取能看到多新的内容。例如，上游刚更新订阅，但缓存只用了 1 分钟，下一次生成仍会使用缓存中的节点；默认 TTL 满 5 分钟后的读取才会重新下载。

## 热重载与预览如何使用缓存

`POST /api/reload` 负责重新读取主配置并使其生效。生产装配使用的 `CachedFetcher` 已实现 `Invalidate(rawURL)`：它删除指定 URL 的一项缓存，保留其余项。`app.Service` 读取远程主配置前先调用此方法，再通过 `Fetch` 读取。

主配置的 TTL 未到也会删除已有缓存项，随后的 `Fetch` 按上一节的规则读取。成功下载的字节会写入缓存，随后再执行 YAML 解析和静态校验。校验失败时，旧的生效配置仍继续使用，具体流程见 [管道设计](pipeline.md#热重载生命周期)。

热重载只清除主配置 URL 对应的项。订阅和模板如果使用其他 URL，其缓存仍然有效；它们会在下一次生成或预览读取时按 TTL 判断是否重新下载。

例如，主配置和订阅使用两个不同的 URL。用户修改了订阅内容，再点“热重载”，服务会刷新主配置，订阅仍可能命中旧缓存。等待订阅 TTL 到期后，再执行生成或节点预览，才会重新下载订阅。

节点预览、分组预览、生成预览和 `/generate` 共用这份缓存。前端点击“重新拉取”会重新请求后端，后端仍按 TTL 决定是否访问上游。

`Invalidate` 只删除调用当时的缓存项，不会取消已经在途的下载，也没有阻止这些下载稍后写回缓存。若需要保证失效前发出的响应永远不能再次写入缓存，需要另行调整这项并发约束。

## 如何验证

- `internal/fetch/fetch_test.go` 检查 TTL 内命中、到期后重新拉取、错误不缓存，以及返回副本不会污染缓存。
- `internal/app/service_test.go` 的 `TestReloadInvalidatesRemoteConfigCache` 检查远程主配置在 TTL 内也会被重载刷新，并确认校验失败时保留旧的生效配置。

在仓库根目录运行 `go test ./internal/fetch ./internal/app` 可执行这些检查。
